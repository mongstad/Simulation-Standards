# Scientific Workflow Simulation Standard (SWSS) v1.1

**Status:** Normative SWSS v1.1 specification, 2026-10-19. **Audience:** Scientific simulation authors and interoperable tool implementers.

This is the self-contained successor to [v1.0](v1.0.md), which is retained as historical text. Specification adoption does not certify a simulation or establish consumer implementation. SimShelf support for the single-file contract requires separately authorized application work; no such implementation is claimed here.

SWSS is a voluntary, independent workflow convention, not an industry certification, new scientific data format, or a dependency requirement on either application. **MUST** is required for the profile claimed; **SHOULD** is recommended with documented exceptions; **MAY** is optional.

## 1. Independent profiles

| Profile | Requirements |
| --- | --- |
| **Core** | General versioning, logs, provenance, isolated outputs, truthful lifecycle |
| **SimShelf** | Core plus SimShelf recorder compatibility, progress, metrics and automatic capture |
| **Wavez** | Core plus verified Wavez WVZ1 scene recording |
| **Full** | Core plus both optional profiles |

A project MUST identify which profiles it claims, tested tool versions and deviations. SimShelf and Wavez remain independent products; users may adopt either or neither. Existing simulations are modernized one by one only when selected for future runs. SWSS is maintained and versioned independently in this repository. Its normative requirements and expected simulation-side behavior are stated here; Core can be used without either application or its documentation. Application repositories own their APIs, formats and implementation guidance. Links to them support integration, do not replace SWSS requirements, and do not automatically revise SWSS when an application changes. Record tested versions and resolve compatibility mismatches explicitly rather than silently changing a claimed SWSS requirement.

## 2. Core profile: scientific integrity

1. Integrating workflow features MUST NOT silently change numerical equations, timestep, grid, precision, RNG stream, boundary conditions or other scientific behavior. Preserve a before/after reference or explicitly document the approved scientific difference.
2. Each run MUST document all experiment parameters and resolved runtime values. Record simulation name, start time, model version, selected Python version, actual arguments, solver configuration (including timestep and boundary conditions), grid extent/resolution, time units, channel/coordinate units, output cadence and random-seed/state policy. SHOULD record dependency versions, GPU/backend/precision, numerical assumptions, source identity, external input hashes and restart lineage. Disclose reproduction limits from floating-point backends, parallel scheduling, dependencies and external inputs. A `summary.json`, when produced, MUST distinguish physically modeled, diagnostic and dimensionless quantities.
3. Source versioning follows MAJOR.MINOR.PATCH. Any accepted modification to the simulation source package (including comments, configuration and logging/export/instrumentation behavior) MUST bump the declared version before the next recorded run. Breaking scientific changes normally use major; substantive scientific revisions minor; corrections/instrumentation patch. Runtime argument differences alone do not bump the source version. Capture exact source bytes/hash independently: matching labels do not guarantee identical code, and matching structural fingerprints do not prove identical behavior. SHOULD warn/block in CI if tracked code changes without version bump; this is an SWSS development recommendation, not a built-in SimShelf auto-bump or enforcement feature. Checks MUST NOT automatically edit research source.
4. Every run MUST write a uniquely named, timestamped, human-readable `.log` file including version, parameters, status and useful errors/tracebacks. UTC timestamp format SHOULD be YYYYMMDDTHHMMSSZ with an additional collision-resistant run ID. Flush/close on normal shutdown and handled failure; forced termination can leave partial evidence. Avoid uncontrolled per-cell progress writes.
5. Each run MUST have a unique output directory, including concurrent runs, and MUST NOT silently overwrite historical output. File paths, parameter conventions, inputs and outputs must be documented.
6. Failure MUST use a nonzero exit code. Incomplete outputs MUST NOT be labeled verified complete. Close text logs, measurement files and any visualization writers on normal completion; on handled failure/interruption, SHOULD close them safely and record the reason while preserving partial evidence. Keep visualization recording and diagnostic/checkpoint cadences independent of the solver integration step. Restart checkpoints MAY be provided but MUST contain the solver state actually needed to resume, with provenance and restart lineage. Wavez scenes are not restart checkpoints.
7. SHOULD provide at least one scientifically meaningful numeric diagnostic where appropriate; otherwise MUST document why none applies. Reported diagnostics MUST use consistent names, documented formulas and units (or explicit dimensionless/unknown units), and actual sampled solver timestamps. MUST compute them from source solver state, distinguish measurements from estimates or visual interpolation, and handle nonfinite outcomes explicitly without disguising errors. A numerical measurement is not an image-derived impression.
8. Large binary results SHOULD remain outside Git history by default and have their own backup strategy; a reference-only artifact is not a backup. Never place credentials in logs/metadata.

### Suggested project layout

```text
simulation/
  simulate.py
  README.md
  requirements.txt
  swss.toml                     # when using companion configuration; parameters optional
  logs/                         # optional convenience mirror
  outputs/
    run_20261018T123000Z_RUNID/
      logs/run_20261018T123000Z_v0.1.1_RUNID.log
      summary.json
      measurements.csv
      simulation_case_20261018T123000Z_RUNID.wvz  # Wavez profile only
      checkpoint.npz            # only if restart is implemented
```

`RUNID` stands for a collision-resistant ID; filenames identify purpose and run identity. File timestamps do not replace solver time. JSON/CSV are recommended independent evidence, not mandatory filenames. Each run's effective output folder is the SimShelf capture source when that profile is used. A second logging handler MAY mirror the same log beside the entry point; mirrors SHOULD have documented retention/rotation that preserves active-run and required research evidence. Exclude generated logs/outputs, environments, caches and large artifacts from source snapshots/Git as appropriate; retain research source and relevant small text evidence.

## 3. Optional SimShelf profile

The simulation MUST be registerable with a stable Python entrypoint and a single `swss.toml` following §6. Shared entrypoint, simulation version and any parameter declarations belong in `[swss]`; application-specific settings belong in `[apps.simshelf]`. Include the companion file and the source version file in source capture. No additional parameter schema file is required or prescribed. Parameter declarations MAY be absent; use manual argv or explicitly selected bounded static discovery in that case.

The simulation MUST retain an explicit human-assigned revision label, distinct from the SimShelf build or WVZ1 format version. For the existing Python version-tag mechanism, declare a literal `SIMSHELF_VERSION` in the selected source version file. Its value and `swss.simulation_version` MUST agree; consumers MUST report mismatches rather than silently choose a label. These are SWSS versioning requirements, not a claim that SimShelf enforces per-change bumps. The label, exact selected source snapshot and structural fingerprint are distinct. Snapshots record startup bytes and do not isolate a running process from later source edits. Discovery is advisory: validate actual accepted arguments and resolved defaults against the script.

**Implementation boundary:** The portable contract in §6 is normative. Mapping SimShelf capture settings into `[apps.simshelf]` requires a future application adapter; the example field names below illustrate that mapping, not verified current reader support. The workflow obligations in this section still apply to implementations claiming this profile. A current application without the reader is not made v1.1-compatible by this document.

### Coordinated run output folders

SimShelf defaults to **Fixed folder (existing behavior)**. The opt-in **Unique subfolder for each run** policy allocates the actual run folder beneath the configured capture parent when the run starts. `SIMSHELF_OUTPUT_DIR` and joined `run.output_dir` identify that same allocated folder. Selecting this policy does not make a non-cooperating script safe, migrate old outputs or redirect writes. The [SimShelf running guide](https://github.com/mongstad/SimShelf/blob/main/docs/RUNNING.md#unique-output-folders-for-cooperating-scripts) explains application controls; the SWSS requirements for the simulation are:

- The script MUST use the supplied folder as its effective run output root and write capturable logs, CSV/JSON, scientific snapshots and optional WVZ1 artifacts beneath it. It MUST NOT append another run directory to establish a separate run root. Artifact subdirectories such as `logs/` remain appropriate. The allocated folder already exists; `mkdir(parents=True, exist_ok=True)` is appropriate when ensuring it exists.
- Explicit simulation `--output` / `--output-dir` arguments MUST NOT silently override the coordinated location. The script MUST either resolve them to that same folder or reject a conflict clearly before writing. SimShelf does not rewrite arguments, expand environment variables inside them or redirect arbitrary file writes. Required artifacts written elsewhere MUST be reported as missing from capture, not assumed preserved.
- Without a recorder-supplied folder, standalone execution MUST deliberately choose a unique output directory, with documented and tested explicit-path precedence. In **Fixed folder** mode, the recorder and script still MUST be configured to use the same unique target for each run. The application's fixed default does not waive Core's isolation rule. Successive and concurrent runs MUST have distinct, non-overlapping output roots, and retain Core's unique run identity and truthful success/failure evidence.

Capture rules and copy/reference budgets are evaluated relative to the allocated run folder. The entire configured parent remains excluded from source snapshots, including earlier sibling runs. Optional Git archival requires separate consent; selecting the output policy does not authorize it. Referenced/original binary artifacts still need independent backups, and Git archival is not a replacement for those backups.

For adoption, select the opt-in policy only after checking the script's output resolution. At run start, use the supplied root directly, then confirm the recorded capture path and actual artifact paths agree. Verify successive and simultaneous runs preserve earlier originals; inspect missing/skipped artifacts separately from solver completion. Wavez export remains optional and follows §4 when claimed.

### Automatic capture and telemetry

**Automatic log capture is required with no post-run upload:** write a timestamped real .log file directly to the effective output folder's logs/ subdirectory. In SimShelf file-capture settings, place a `copy` rule matching `**/*.log` before any broader matching rule, and verify file/run size budgets. For successful capture validation, SimShelf MUST automatically show that log in the run's Files record after final capture. Native recorded process stdout/stderr MUST also be available in Logs, subject to recorder retention limits; it does not replace the timestamped file. A second logging handler MAY also create a local mirror next to simulate.py; source-adjacent logs alone are NOT automatically ingested by current output-directory capture. Avoid symlinks. Verify normal, failed and cancelled runs and inspect skipped/oversized artifacts. Capture validation MUST report missing/skipped/oversized required logs as incomplete, separately from solver success. File capture may remain incomplete after interrupted processes.

For a future SimShelf adapter, the following **illustrative fragment** belongs inside the single `swss.toml`, **before any broader matching rule**. Confirm the effective File capture settings used by the next run; §6.6 supplies a complete mixed-use example:

```toml
[[apps.simshelf.capture.rules]]
pattern = "**/*.log"
action = "copy"
```

This fragment does not configure a unique output directory or size budgets; those must also be set and verified. Default capture limits are 25 MB per file and 200 MB per run, not a promise to retain every log. Final capture inventories new/changed files by size and modification time, excludes symlinks, and can miss rewrites that preserve both. Unique run paths and closed files avoid relying on that detection for old artifacts.

Finite jobs MUST report truthful progress by default; intrinsically indeterminate work MUST use stage descriptions without a fabricated percentage. Both structured and parsed progress require an explicitly enabled compatible library; follow the application's backup/restore and older-writer compatibility procedure before enabling it. Use the structured `run.progress(current=..., total=..., stage=...)` API with the SimShelf package installed in the selected interpreter, OR print a whole-line supported form such as `Step 1000 of 50000` with flushing and explicitly select the **Step counts** parser. Neither adapter is universal automatic inference. SHOULD rate-limit reports and measure instrumentation overhead. Do not conflate step counts with scientific time or consider 100% proof of successful computation. Completed-run display values can be synthesized from process completion; the stored last report is separate, and progress is not a scientific time series.

Where scientifically meaningful, SHOULD call run.metric(name, value, step=..., sim_time=...) from a joined run context, using finite, correctly defined quantities that satisfy Core diagnostic requirements. Invalid/nonfinite measurements can raise in the caller; record and handle such outcomes explicitly. SHOULD also save independent measurements.csv and summary.json. SimShelf does not infer arbitrary log numbers as stored scientific metrics.

Small text JSON/CSV/logs and useful preview images SHOULD usually be copied according to configured limits; large binary captures/checkpoints SHOULD usually be referenced with independently verified backups. File capture rules are prospective, first-match-wins; a source-local .log outside the watched folder is not included merely because it exists.

## 4. Optional Wavez profile

Use the currently supported WVZ1 .wvz format via wavez_export.SceneCapture and its documented reader. Do NOT create obsolete SSC/SIMSCP4 outputs or mislabel a custom file. Preserve actual solver timestamps, scientific units and coordinate meanings; use supported particle/mesh ID semantics and valid volume shape (nz,ny,nx) with xyz origin/spacing. Channel names must reflect actual solver quantities. Declare coordinate transformations, centering and channel meaning explicitly; unknown units remain unknown. Do not invent persistent IDs from row order or silently normalize/narrow scientific values for display. Represent complex fields through documented real components and retain full restart/scientific state separately when needed. The integration guide supplies application-specific geometry and identity API details supporting these SWSS requirements.

### Capture names and run identity

Following [Core's unique-output requirement](#2-core-profile-scientific-integrity), each WVZ1 capture MUST use a new, unused full path. Default filenames SHOULD combine a stable simulation identifier, experiment/case label, UTC timestamp (`YYYYMMDDTHHMMSSZ`) and collision-resistant run ID: `<simulation>_<case>_<UTC timestamp>_<run ID>.wvz`. For example, `vacuum_collapse_D_20261018T164500Z_RUNID.wvz` uses `RUNID` as a placeholder for a full collision-resistant identifier, not a literal suffix. A timestamp alone is insufficient for runs started within the same second. Generate identity independently of the scientific RNG stream.

The same run identifier MUST correlate the capture, log and associated metadata/diagnostic manifests. Record the run ID and resolved capture path in run provenance; multiple captures within one run MUST have distinct artifact labels or sequence suffixes while retaining that run ID. Unique per-run directories can establish full-path uniqueness even when basenames repeat; in that case, document the directory-to-run mapping and still SHOULD use descriptive filenames.

Naming is a simulation-side SWSS convention, not automatic naming by Wavez. Preserve the [Wavez API's exclusive creation](https://github.com/mongstad/Wavez/blob/main/WAVEZ_API.md): captures MUST NOT automatically replace existing files. Collision-resistant names reduce accidental collisions; exclusive creation is the final protection, including concurrent creation races. An explicitly supplied `--wavez-file` (if the simulation offers it) MUST designate a new unused path or fail clearly. It MUST NOT be silently renamed; any alternative-path behavior requires documented, explicit opt-in and recording of the actual path. An existence check alone MUST NOT replace exclusive creation.

An existing destination is a naming collision, distinct from permission denial, invalid/missing parent paths or insufficient disk space. Report the actual failure and destination; unique names do not prevent all filesystem errors. Follow the failure and partial-evidence requirements below.

### Recording and validation

Recording cadence MUST be configurable independently of integration timestep, and recording MUST NOT change scientific RNG calls or solver state. Do not silently overwrite captures. Finalize the writer correctly; partial captures must not be declared verified complete. Each requested `.wvz` artifact MUST undergo matching `SceneReader` validation before being described as verified, with actual payload readback and documented coverage. Acceptance MUST include numerical comparisons against source samples (values/dtypes, geometry, timestamps, units and channels), identity-history checks where applicable, and a viewer inspection on a representative short file. Viewer playback alone does not recompute payload SHA and is not an integrity test. An incomplete trailing record may be inspected with `strict=False`, but that does not accept corruption or establish a complete run. Export failures MUST be reported truthfully; document whether the solver stops or continues and how independent scientific archives are preserved. After an I/O failure the writer is unusable: retain the committed prefix and use a new destination, not writer resume. WVZ1 is visualization data, not a universal restart state. A capture toggle MAY reduce cost, but a Wavez profile claim requires a supplied and tested export path.

## 5. Acceptance and adoption

For **Core**, verify unique paths, version/provenance, truthful success/failure, log and numeric baseline before/after integration. For **SimShelf**, verify discovered settings, correct effective output folder, live progress using a supported selected adapter, metrics if meaningful, native process Logs, and an automatically captured timestamped .log under Files with **no manual upload**. For **Wavez**, verify the real WVZ1 output with both SceneReader numerical comparisons and a Wavez viewer inspection. For consumers claiming the optional parameter capability, apply §6.7; simulations without parameter declarations do not acquire a new obligation to add them. Run a successful short job, an intentional failure and a handled cancellation where safe; record untested paths. SimShelf acceptance also MUST exercise two simultaneous runs with distinct capture targets, inspect copy/reference budgets and independently compare recorded metrics with solver diagnostics. Wavez acceptance MUST compare export enabled/disabled numerical state and RNG behavior. It MUST also run two consecutive captures with identical scientific parameters using default destination selection, verify distinct paths and separately readable WVZ1 payloads, confirm the first artifact remains unchanged, and check run-ID correlation with logs/metadata. Test an explicit-path collision: it must fail clearly without replacing the existing capture or silently writing to an alternative path when no opt-in is enabled. Verify independent backups for source and referenced artifacts. See the [review gates](../../docs/REVIEW.md).

The first SWSS reference implementation and automated version consistency checks are **future work**, not current certification. Validate one small synthetic simulation before adopting any legacy simulation. No mass migration or historical-data rewrite is required. A reusable starter/helper is future work subject to separate owner approval. Automatic external-log ingestion, automatic source-version bumps, embedding WVZ1 in the SimShelf database, cloud upload, video-derived scientific ground truth and restart from WVZ1 are outside v1.1 requirements.

## 6. Optional single-file configuration and parameter metadata

This section defines schema version **1** within SWSS **1.1**, not a new profile. Parameter declarations and source hashes are optional; existing scientific workflow guarantees remain in §§1–5. A file that participates MUST satisfy the header/schema rules even when parameter rows are absent. No extra manifest or application installation is required for portable typed controls.

The portable section describes command-line inputs for one entrypoint, not solver configuration, execution commands or a source of runtime defaults. SWSS owns these semantics; applications adapt to them. The simulation script remains authoritative for parsing, validation, defaults and scientific behavior. Consumers MUST present metadata as advisory, not proof of runtime compatibility or scientific correctness.

### 6.1 Location, association and adoption

Participating simulations MUST use **one `swss.toml` at the simulation root**, containing a reserved `[swss]` section and optional `[apps.<application>]` tables. A Python simulation plus this one companion file MUST suffice for these declarations and participating applications' project configuration; no second TOML file or generated shadow configuration is required. A root is an explicitly selected project directory, not one guessed by walking parents. One document describes one simulation entrypoint. Multi-entrypoint project orchestration is outside this capability; no recursive discovery, includes, overlays or file merging is permitted.

The only portable discovery path is `swss.toml` directly beneath that root. Its `swss.entrypoint` MUST exactly match the selected launch entrypoint's normalized root-relative path. A mismatch disables typed use with an explanation; it never changes the selected program. The portable section MUST NOT select an interpreter, shell, executable, working directory or environment. Application settings are not executed or interpreted by portable metadata discovery.

#### Application adoption

**`swss.toml` is the sole configuration file for participating simulations.** SWSS defines the portable contract; SimShelf will read it, with application settings under `apps.simshelf`. Other applications use their own namespaces. No continuing `simshelf.toml` support, dual-file selection/merging, migration wizard, automatic conversion, shadow configuration or rollback compatibility layer is required or specified. Portable discovery reads only `swss.toml`; other filenames are not candidate configuration sources.

Adoption is deliberate work in separately authorized implementation changes:

1. Update SimShelf's configuration reader and all affected launch, capture and discovery paths to consume the single `swss.toml` contract.
2. Update participating simulations' configuration files to that format: shared identity and parameters in `swss`, application settings in `apps.simshelf` or the appropriate namespace. Authors check their settings and argv; discovery MUST NOT write or convert configuration files.
3. Validate the complete application path and participating configurations before release. Once the new implementation is validated, remove the old reader outright. Do not release a partially converted application whose entry points disagree about the configuration file. No permanent compatibility adapter is needed.

Retiring configuration parsing MUST NOT alter or delete existing run records, historical source snapshots (including old configuration bytes), recorded argv, artifacts or scientific provenance. History remains evidence of what actually ran; do not rewrite it to the new format. Preserving historical evidence does not require using historical configuration as input to new runs. New runs use the new configuration and record their own provenance. The simulation script remains authoritative for argument parsing and scientific behavior.

Optional parameter declarations do not change existing profile obligations. Core and Wavez users need no companion file unless participating in this configuration capability; the SimShelf profile requires its configuration in this file but does not require parameter rows. It does not require a future SimShelf release to retain its old configuration reader. A missing `swss.toml` means no portable metadata is available; an application needing configuration for a new run reports that requirement rather than searching for or converting an old file. Manual argument editing remains available, subject to independent launch requirements.

The companion-file path and portable entrypoint/source-manifest paths MUST use `/` separators and relative components, excluding empty components, `.`, `..`, leading `/`, backslashes, drive/URI prefixes and control characters. Resolve within the selected root; reject symlinks in the candidate or any referenced path component, escapes, non-regular files and inaccessible paths. Do not expand `~`, environment variables or globs. A selected root itself may be canonicalized once with user knowledge; all checks then use that root. Recheck identity when reading to avoid a check/open substitution; if a consumer cannot establish safe access, it MUST decline metadata use, not weaken containment.

Discovery and argv precedence:

1. **Existing/manual argv remains authoritative user intent.** Discovery never overwrites tokens, even when declarations change.
2. A valid `swss.toml` supplies portable parameter metadata. Consumers MUST NOT merge it with other configuration files, legacy JSON declarations or static discoveries. No alternative metadata file is required by this contract.
3. Absent, invalid, stale or unsupported metadata yields a visible diagnostic and manual fallback, without silently switching to another source. An application MAY separately offer explicitly selected, bounded static discovery; it MUST identify that source, preserve argv and not present it as the SWSS declaration. No static discovery implementation is required here.

Missing/invalid `[swss]`, entrypoint mismatch and unsupported schema versions disable typed use. A valid partial declaration remains the selected source: undeclared and unsupported options stay manual, rather than being silently supplemented from AST discovery. Duplicate keys are parse errors; duplicate parameter IDs or alias ownership are document-wide ambiguity errors, not last-wins rules. Independent application safety/configuration checks may still prevent launch; manual fallback is not a bypass for them.

### 6.2 Data schema

Use UTF-8 **TOML 1.0.0** syntax. Consumers MUST reject duplicate keys and invalid TOML, and accept only the following schema. TOML syntax is defined by the [TOML specification](https://toml.io/en/v1.0.0); all parameter semantics and limits are stated here. Only root tables `swss` and optional `apps` are allowed. Unknown fields or structures within `swss` invalidate portable metadata use; application-owned fields are handled separately below. New schema versions require explicit consumer support, not best-effort reinterpretation.

| Field within `[swss]` | Requirement |
| --- | --- |
| `schema_version` | Required integer `1`, not a boolean or string. |
| `entrypoint` | Required root-relative regular-file path, bound to the selected entrypoint. |
| `simulation_version` | Required nonempty string identifying the declared simulation source revision; distinct from the schema version and SWSS revision. |
| `parameters` | Optional array of parameter tables; zero through 128 entries. Omitted or empty means no typed declarations, not no CLI arguments. Manual argv remains usable; this is not a schema error. |
| `source_files` | Optional array of `{path, sha256}` tables, unique paths. Each hash is 64 lowercase hexadecimal characters over exact file bytes. If present, include the entrypoint. No other fields. |

`[[swss.parameters]]` contains the parameter rows below; optional `[[swss.source_files]]` contains bindings. A third-party consumer MUST be able to use these tables without installing or consulting any application. `swss.schema_version` versions only the portable section, not application schemas.

`apps` MUST be a table of application tables keyed by a stable lowercase ASCII identifier matching `[a-z][a-z0-9_-]{0,63}` (for example `simshelf`). Applications own their nested settings and any application schema-version field. All consumers MUST enforce whole-file syntax and resource limits, but portable readers MUST ignore application semantics, including unknown application names, fields or schema versions. They MUST NOT interpret application data as SWSS defaults, parameters, source bindings or executable instructions. An invalid application configuration may prevent that application's launch, but MUST NOT make otherwise valid portable metadata invalid for other tools. Malformed TOML or a whole-file safety-limit violation affects all readers because there is only one document.

Application sections MUST NOT redefine or override the portable entrypoint, simulation version, parameter declarations or argv semantics. Consumers MUST use the shared fields in `swss`; no precedence contest between duplicated definitions is specified. A consuming application MUST diagnose conflicting duplicates in its own section and decline use of that application configuration until resolved. Unrelated tools need not understand those fields. Capture/preview settings belong to the application namespace; their interpretation is an application responsibility, not new SWSS capture semantics. No application section is mandatory. Do not put credentials in this shared, source-captured file; use separately managed application credentials instead.

Each parameter requires `id`, `kind`, `required`, `type`, `action`, `help`; `options` or `name` depends on kind. Optional fields are `choices`, `default`, `repeatable` (boolean, defaults to false). No implicit `required`, `type` or `action` is inferred.

| Parameter field | Meaning and constraints |
| --- | --- |
| `id` | Stable within the entrypoint across revisions; ASCII `[a-z][a-z0-9_]{0,63}`. It is not a CLI token or Python destination. A changed scientific meaning SHOULD receive a new ID; renaming never migrates argv automatically. |
| `kind` | `option` or `positional`. |
| `options` | For options only: 1–8 exact case-sensitive aliases, no duplicates. Each matches `--[A-Za-z][A-Za-z0-9_-]*` or `-[A-Za-z]`. First alias is the preferred new-control spelling, never a replacement for saved aliases. `--`, embedded `=`, whitespace, short bundles and abbreviations are not aliases. |
| `name` | For positionals only: a descriptive ASCII identifier using the same grammar as `id`. It is a label, never emitted as a token. |
| `required` | Boolean: whether the parser requires presence, not whether a default hint exists. A supported value option always takes exactly one value when present, even if `required = false`. |
| `type` | `integer`, `float`, `string` or `boolean`. Booleans are no-value flags, not value-taking `true`/`false` options. |
| `action` | `store` for integer/float/string options; `store_true` or `store_false` for boolean options. Positionals use `store` and a non-boolean type but are manual-only. |
| `help` | Human-readable description, plain text; empty allowed, never interpreted as markup, templates or commands. |
| `choices` | Optional nonempty array of at most 100 distinct values of the declared type. Not supported for flags. An explicitly supplied default must be a member. |
| `default` | Optional scalar of the declared type, informational only. Absence means unknown; `default = ""` is a known empty-string hint. TOML has no null value: do not invent a sentinel for `None`. |
| `repeatable` | True marks the row manual-only. No append/count/collection serialization is specified. |

Integer hints/choices MUST be TOML integers in signed 64-bit range, excluding booleans. Float hints/choices MUST be finite TOML floats, excluding integers and booleans; use binary64 numeric equality for duplicate/membership checks (`-0.0` equals `0.0`). String hints/choices MUST be TOML strings. Flags permit only boolean defaults. A default need not equal the usual argparse implicit default, since parsers can override defaults; it never determines token presence.

For supported value controls, validate integer text against `[+-]?[0-9]+` and signed 64-bit range, and float text against `[+-]?(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)(?:[eE][+-]?[0-9]+)?` with a finite binary64 result. This is a deliberately narrow portable editing subset, not a claim about every parser's grammar. Preserve the original text after validation: `00192`, `+192`, `1e-3` and `0.001` are not interchangeable argv spellings. Choices compare parsed numeric values or exact string values; display labels cannot replace tokens. Other numeric forms remain possible through manual editing, subject to the script's parser.

Positionals, repeated occurrences, `repeatable = true`, unsupported type/action combinations, unknown row fields (such as `nargs`), or otherwise invalid individual rows (except document-wide errors specified below and safety-limit failures in §6.5) MUST be labeled manual-only with a reason. Do not partially interpret that row. Other valid rows MAY remain typed. Missing/invalid IDs or option alias lists, duplicate IDs, or aliases claimed by different rows invalidate the whole document because ownership is ambiguous. A syntactically valid but unsupported action such as `append` may retain its unique ID/aliases for diagnostics only. Mutually exclusive groups, paired boolean actions sharing a destination, subcommands, custom converters and multiple-value options have no typed semantics in schema 1 and MUST use manual handling; authors MUST NOT misdeclare them as independent scalar controls.

### 6.3 Exact argv contract

A consumer MUST maintain one ordered list of argument strings, independent of presentation groups. Opening, rescanning, changing source, saving/reloading or changing metadata MUST preserve existing tokens byte-for-byte in their UTF-8 representation and in the same order. Do not insert defaults, resolve aliases, deduplicate repeats, combine/split tokens, normalize numbers, expand variables or execute a shell. Only explicit user edits may change tokens; show the resulting exact argv before launch.

- Supported long `--name=value` splits at the first `=` only for presentation; preserve the original form on save. Separate `--name`, `value` and short `-n`, `value` forms remain separate. No inference for short attached values or bundles. Values may contain further `=` characters.
- A flag control means **emit this option**, not set the resulting scientific value. Enabled `store_true` emits only its alias (parser sets true); enabled `store_false` emits only its alias (parser sets false). Disabled emits nothing. Do not fabricate opposite flags, `false`, empty values or defaults. Required flags still need deliberate inclusion.
- Absence, a token with no following value, and an explicit empty string are distinct. For example `[]`, `["--label"]`, `["--label", ""]` and `["--label="]` MUST remain distinct representations. A supported string control can explicitly request an empty string; a blank manual value field MUST NOT silently add one. A missing value for a known scalar is a diagnostic, not authority to repair argv.
- Tokens after the first standalone `--` are manual positional content, even if they look like options. Unknown tokens, repetitions and ambiguous token/value pairings MUST stay manual and retain order. When pairing would consume a known option token as a value or has uncertain ownership, decline typed mapping; do not guess missing values. A negative numeric token matching the declared grammar may be a separate numeric value.
- On explicit edits to an unambiguous existing row, replace/remove only that row's identified token span in place. Newly enabled options MUST be inserted at a user-visible, confirmed position (default: immediately before `--`, otherwise at the end), without moving existing tokens. Use the first alias unless the user selects another; new long scalar options use `--name=value`, new short ones use two tokens. New flags use one token. Choice selection MUST preview the exact token text before acceptance, including any consumer-generated numeric spelling.

Metadata validation MAY prevent a typed edit from being accepted until corrected. It MUST NOT strand otherwise usable manual argv: offer explicit manual editing without metadata-based launch rejection, subject to the runner's independent safety/launch checks. The simulation may still reject those arguments. Never downgrade a known validation error silently or claim manual mode validates it.

### 6.4 Consistency and provenance

Authors MUST maintain declarations alongside source and bump the simulation source revision under their claimed SWSS versioning policy when changing this source-package metadata. `simulation_version` labels the revision the declaration describes; it is not an automatic version bump. Store declarations with captured source when used. Consumer writes to simulation files or automatic synchronization are not authorized by discovery.

Source manifests are optional: basic typed controls MUST work without them, with **binding unverified** shown. If `swss.source_files` is provided, consumers MUST hash the listed files as data and compare each entry before enabling typed use. A missing file, unsafe path or mismatched digest makes the binding stale/invalid and disables typed use. A declared version mismatch against a separately available, safely obtained simulation version also disables typed use; never import source to obtain it. Without hashes or a comparable version, display **binding unverified**, not **current**. Matching hashes prove only listed bytes match, not runtime semantics or completeness of a source package. Imported modules, dependencies and environment changes can invalidate behavior even with a matching entrypoint.

On rescan or before launch, recheck the whole companion-file bytes and any supplied bindings. Changes MUST invalidate the previous metadata-based preview, preserve argv and require review before reusing typed controls. A source change after the check remains possible; disclose the check's timing and do not claim isolation. Oversized source hashing is **binding unverified / manual-only**, not permission to skip a supplied binding and label it verified.

When declarations are used to configure a recorded run, consumers MUST retain the root-relative declaration path, exact companion-file bytes and SHA-256 (including application sections), portable schema version, declared simulation version, selected entrypoint, selected discovery source, binding status/reasons and checked source hashes (if any), plus the final exact argv. Runtime resolved parameters remain separate scientific provenance. If a declaration later becomes invalid or is bypassed, retain its last-used provenance and the bypass/review decision; a new manual run need not invent metadata. Do not record absolute workstation paths or credentials solely for this convention. Consumers must use their existing safe provenance storage; this specification mandates no database schema or migration.

### 6.5 Safety and bounds

Discovery MUST parse data only: no imports, evaluation, `--help`, subprocesses, plugins, command interpolation, network fetches or dependency installation. Render descriptions as text. Declaration values do not authorize file writes or select executable code.

Interoperable limits (exceeding any is a visible document failure with manual fallback): File bytes, depth, total entries and string bounds apply to the entire mixed-use file, including ignored application tables; parameter-specific limits apply within `swss`: **262,144 bytes** per document; nesting depth **8** (root table depth 1; each contained array/table adds 1); **4,096 total keys and array elements**; **128 parameter rows**; **8 aliases per row**; **100 choices per row**; **32 source files**; **4,096 UTF-8 bytes per string**, except **1,024 per path** and **128 per alias**. Strings MUST exclude NUL and control characters U+0000–U+001F/U+007F, except LF/tab in portable `help` and application text strings. Nonfinite numeric values invalidate the document. Within `swss`, dates/times and nested values outside specified structures invalidate portable metadata. Within application tables, TOML data types and nested tables/arrays are allowed within the whole-file bounds; portable consumers do not apply application schemas or dereference application paths. Scalar row type errors use the manual-row rule in §6.2; safety/count/string-limit failures invalidate the document.

Consumers MUST bound parsing work/memory as well as input bytes; reject excessive nesting before allocating unbounded structures (a bounded parser or isolated resource-limited parse is acceptable). Source hashing is streaming, limited to **16 MiB per file / 64 MiB total**. Consumers with tighter local limits MUST disclose them and fall back manually rather than claim full schema-1 support for all valid inputs. A source above the AST node limit can still use metadata because no AST is required; source exceeding hash limits cannot use a supplied verified binding in this revision. Manual argv remains available regardless of discovery failure, subject to independent runner safety constraints.

### 6.6 Examples

This single `swss.toml` example combines portable parameters and an illustrative application capture section. It intentionally omits source hashes: its binding is unverified, but its typed controls remain usable. It is illustrative and makes no claim about any scientific solver's defaults. A real author must choose and validate the values against their parser.

```toml
[swss]
schema_version = 1
entrypoint = "simulate.py"
simulation_version = "0.1.1"

[[swss.parameters]]
id = "grid_size"
kind = "option"
options = ["--N", "-n"]
required = false
type = "integer"
action = "store"
help = "Grid resolution along each axis"
default = 192

[[swss.parameters]]
id = "timestep"
kind = "option"
options = ["--dt"]
required = true
type = "float"
action = "store"
help = "Integration timestep in model time units"

[[swss.parameters]]
id = "precision"
kind = "option"
options = ["--precision"]
required = false
type = "string"
action = "store"
help = "Arithmetic precision"
choices = ["single", "double"]
default = "double"

[[swss.parameters]]
id = "wavez"
kind = "option"
options = ["--wavez"]
required = false
type = "boolean"
action = "store_true"
help = "Write visualization output"
default = false

[[swss.parameters]]
id = "plots"
kind = "option"
options = ["--no-plots"]
required = false
type = "boolean"
action = "store_false"
help = "Disable plots"
default = true

[[swss.parameters]]
id = "label"
kind = "option"
options = ["--label"]
required = false
type = "string"
action = "store"
help = "Optional annotation"
default = ""

# Illustrative future application settings, not current SimShelf support.
[apps.simshelf.capture]
output_dir = "outputs"
max_file_mb = 25
max_run_mb = 200

[[apps.simshelf.capture.rules]]
pattern = "**/*.log"
action = "copy"

[[apps.simshelf.capture.rules]]
pattern = "**/*"
action = "reference"
```

A minimal companion file with no parameter declarations is valid:

```toml
[swss]
schema_version = 1
entrypoint = "simulate.py"
simulation_version = "0.1.1"
```

A new tool-neutral simulation can use the mixed-use example with the `apps` tables omitted; no replacement or second file is needed. A third-party parameter reader extracts only `swss`. The example application keys illustrate where capture settings could move; their exact application schema and validation require separately reviewed SimShelf implementation work.

These rows correspond, respectively, to ordinary argparse declarations with `type=int`, `type=float, required=True`, `choices=["single", "double"]`, `action="store_true"`, `action="store_false"`, and `type=str`. The declared defaults must be supplied to the parser where applicable; the metadata does not supply them. No source code is executed to discover these rows. A declaration may describe another CLI implementation with the same behavior.

Intentional malformed fixture (not a valid configuration): duplicate portable key; consumers MUST reject the whole document:

```toml
[swss]
schema_version = 1
schema_version = 2
```

Ambiguous example mutation: append a copy of `grid_size` with a new ID but the same `--N` alias; reject the entire document. Unsupported-row mutation: add `nargs = "+"` to `grid_size`; mark that entire row manual-only, keep other valid rows. Unsafe mutation: set `swss.entrypoint` to `"../outside.py"`; reject before reading that path. Unknown default: omit `default`; `default = null` is invalid TOML, while `default = "null"` is a literal string and invalid for a numeric row.

### 6.7 Conformance cases

A consumer claiming this capability MUST satisfy the applicable cases below; they define required outcomes, not claims that any implementation has passed. Application-adoption and historical-evidence cases apply to applications adopting the contract. Start with the complete example and a harmless matching entrypoint; mutations below specify the fixture input and required outcome.

| Fixture | Expected result |
| --- | --- |
| Omit `swss.parameters`, or set `parameters = []` under `[swss]` | Valid header-only declaration; no typed controls/default insertion; manual argv available; no loss of profile compliance. |
| Valid mixed-use example; no argv | Six portable typed rows; application settings not used by discovery; hints only; no tokens inserted; missing required `--dt` diagnostic with manual escape; binding unverified. |
| Exact mixed argv: `["--N", "00192", "--dt=1e-3", "--label", "", "--unknown", "--", "--wavez"]` | Open/rescan/save/reload preserves every token; unknown and post-delimiter content manual; no trailing flag inferred. |
| `--label=a=b`, `--label=`, `--label` without value | First split only; explicit empty retained; missing value diagnosed without repair. |
| Numeric/string choices, default hints and type errors | Accept values of the declared type and choice set without inserting defaults; preserve numeric spelling. Wrong scalar type, out-of-choice value or invalid default yields a diagnostic/manual row, never coercion. Boolean values are not integers; nonfinite values fail the whole-file safety rule. |
| Enable each boolean flag independently; then disable | One exact option token per enabled flag, none when disabled; no flag value or opposite token. |
| Append positional `kind="positional", name="input", type="string", action="store"` with ID/help/required and no options | Manual label only; no fabricated position, name token or arity. |
| Repeated `--N`, `-n`; unknown option before apparent value | Preserve order/aliases; manual ambiguous ownership, no last-wins or duplicate removal. |
| `repeatable=true`, `action="append"`, or unknown row `nargs` | Manual-only affected rows, diagnostics; supported rows remain usable. |
| Duplicate key, duplicate ID/alias, bad header, schema 2 | Whole-document diagnostic; preserve argv, no silent metadata-source fallback. |
| Partial valid document omits `precision` | Remaining typed rows work; precision stays manual even if AST could find it. |
| `swss.toml` and unrelated metadata/static declarations disagree | Only SWSS file supplies portable declarations; no merge or automatic source switch; exact saved argv preserved. |
| `swss.toml` missing; another TOML exists | Missing-metadata diagnostic and manual fallback; no substitute file, recursive search or conversion. Application configuration requirements remain explicit. |
| New project with only Python and `swss.toml`, no `apps` tables | Portable discovery works with no application installation, manifest or second config file. |
| Complete SimShelf adoption with participating configurations | All affected launch/capture/discovery paths read `swss.toml`; validate new behavior before retiring old parsing or releasing. No generated compatibility files. |
| Historical run recorded before adoption | Records, snapshots, old config bytes, argv, artifacts and provenance remain unchanged and inspectable after reader retirement. No historical rewrite. |
| Unknown application namespace/version or application-semantic error | Portable fields still usable by other tools; application reports its own unsupported settings. No semantic interpretation of ignored tables. |
| Duplicate shared identity inside `apps.simshelf` conflicts with `swss` | SimShelf refuses conflicting app configuration; shared portable fields never overridden. |
| Valid portable section plus malformed/oversized/deep application section | Whole-file syntax/resource failure; ignoring app semantics does not bypass safety limits. |
| Modified companion bytes (including app-only edit), mismatched version, changed/missing hashed source | Invalidate preview and stale typed use, preserve argv/provenance; require review or explicit manual bypass. |
| Exact listed hashes; unlisted imported module changed | Binding says listed bytes match only; no semantic/conformance guarantee. |
| Source exceeds 20,000 AST nodes, metadata within limits | Metadata discovery requires no AST, imports or bound relaxation. Hash files within limits normally; oversized hashing falls back as specified. |
| Absolute/traversal/symlink/URI path or entrypoint mismatch | Refuse metadata association safely, preserve selected program and argv. |
| 262,145-byte file, depth 9, 129 rows, 9 aliases, 101 choices, 33 source entries, oversized strings/hash input | Enforce each stated limit and documented fallback; test exact allowed boundary too. |
| Invalid UTF-8, NUL, nonfinite float, date value in `swss` | Reject invalid portable metadata; a finite but wrong scalar type yields row fallback. No execution side effects. |
| Help or string value contains shell syntax | Display text, preserve explicit user argv as data; never evaluate it. |
| Declaration modified between safe open and preview/launch | Detect identity/byte change where checked; refuse reuse, disclose post-check race limit. |

Conformance tests MUST assert no filesystem writes, imports, subprocesses or network activity during discovery, and verify provenance captures the exact declaration that informed user edits rather than a later file version.
