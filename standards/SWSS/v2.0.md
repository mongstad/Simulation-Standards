# Scientific Workflow Simulation Standard (SWSS) v2.0

**Status:** Normative text submitted for owner review, 2026-10-19; not a release, ratification or implementation certification. **Audience:** Scientific simulation authors and tool implementers.

SWSS is one independent, voluntary scientific workflow standard. Anyone may adopt or ignore it. The simulation remains independently executable and authoritative for argument parsing and scientific behavior. No particular recorder, viewer, library or binary format is required. **MUST** denotes an obligation for the claimed baseline or capability; **SHOULD** denotes a recommendation with documented exceptions; **MAY** denotes an option.

## 1. Scope, claims and compatibility

A simulation claiming SWSS v2.0 MUST meet the baseline in §2. Optional capabilities in §§3–4 are independent: adopting one never requires another. A tool claiming a capability MUST implement its consumer obligations and document its tested version, coverage, deviations and limitations. A parameter editor alone need not implement a solver, recorder or viewer and MUST NOT imply baseline simulation conformance. Simulation authors remain responsible for baseline scientific evidence.

| Claim | Additional requirements |
| --- | --- |
| Baseline | Scientific integrity, source versioning, exact arguments, isolated outputs, logs, provenance and truthful lifecycle (§2). |
| Coordinated run capture | Shared output root, automatic log/artifact preservation and capture evidence (§3.1). |
| Progress and metrics | Truthful telemetry, documented diagnostics and independent measurements (§3.2). |
| Scientific export | Non-destructive artifacts, documented formats and numerical readback (§3.3). |
| Portable configuration and parameter editing | One `swss.toml`, optional parameter rows, bounded data-only discovery and exact argv (§4). |

**Breaking revision:** v2.0 replaces the earlier product-oriented profile taxonomy with the claims above. Old profile labels do not imply v2.0 conformance. The portable schema becomes **2** because root `apps` tables are replaced by generic optional `extensions`; schema 1 MUST NOT be silently reinterpreted as schema 2. Parameter row and exact-argv semantics remain unchanged. Authors review configurations and claims deliberately; no automatic converter, extra file, compatibility shim or rollback layer is prescribed. Validate all affected consumer paths before retiring an old reader or releasing an adoption. No external implementation is updated by this specification.

The tracked [v1.0 summary](v1.0.md), [v1.1 summary](v1.1.md) and [earlier proposal summary](../../docs/proposals/0016-parameter-metadata.md) explain their archival status. Original revisions remain in Git history. Historical run records, snapshots (including configuration bytes), exact argv, artifacts and scientific provenance MUST NOT be rewritten or discarded during adoption. New runs record their own contract version and evidence. Preserving history does not require launching new runs with old configuration.

## 2. Baseline scientific integrity

1. Integrating workflow features MUST NOT silently change numerical equations, timestep, grid, precision, RNG stream, boundary conditions or other scientific behavior. Preserve a before/after reference or explicitly document the approved scientific difference.
2. Each run MUST document all experiment parameters and resolved runtime values. Record simulation name, start time, model version, selected language/runtime version (including Python where used), actual arguments, solver configuration (including timestep and boundary conditions), grid extent/resolution, time units, channel/coordinate units, output cadence and random-seed/state policy. SHOULD record dependency versions, GPU/backend/precision, numerical assumptions, source identity, external input hashes and restart lineage. Disclose reproduction limits from floating-point backends, parallel scheduling, dependencies and external inputs. A `summary.json`, when produced, MUST distinguish physically modeled, diagnostic and dimensionless quantities.
3. Source versioning follows MAJOR.MINOR.PATCH. Any accepted modification to the simulation source package (including comments, configuration and logging/export/instrumentation behavior) MUST bump the declared version before the next recorded run. Breaking scientific changes normally use major; substantive scientific revisions minor; corrections/instrumentation patch. Runtime argument differences alone do not bump the source version. Capture exact source bytes/hash independently: matching labels do not guarantee identical code, and matching structural fingerprints do not prove identical behavior. SHOULD warn/block in CI if tracked code changes without version bump; this is a development recommendation, not a claim of automatic enforcement. Checks MUST NOT automatically edit research source.
4. Every run MUST write a uniquely named, timestamped, human-readable `.log` file including version, parameters, status and useful errors/tracebacks. UTC timestamp format SHOULD be YYYYMMDDTHHMMSSZ with an additional collision-resistant run ID. Flush/close on normal shutdown and handled failure; forced termination can leave partial evidence. Avoid uncontrolled per-cell progress writes.
5. Each run MUST have a unique output directory, including concurrent runs, and MUST NOT silently overwrite historical output. File paths, parameter conventions, inputs and outputs must be documented.
6. Failure MUST use a nonzero exit code. Incomplete outputs MUST NOT be labeled verified complete. Close text logs, measurement files and any visualization writers on normal completion; on handled failure/interruption, SHOULD close them safely and record the reason while preserving partial evidence. Keep visualization recording and diagnostic/checkpoint cadences independent of the solver integration step. Restart checkpoints MAY be provided but MUST contain the solver state actually needed to resume, with provenance and restart lineage. Visualization artifacts alone are not restart checkpoints.
7. SHOULD provide at least one scientifically meaningful numeric diagnostic where appropriate; otherwise MUST document why none applies. Reported diagnostics MUST use consistent names, documented formulas and units (or explicit dimensionless/unknown units), and actual sampled solver timestamps. MUST compute them from source solver state, distinguish measurements from estimates or visual interpolation, and handle nonfinite outcomes explicitly without disguising errors. A numerical measurement is not an image-derived impression.
8. Large binary results SHOULD remain outside Git history by default and have their own backup strategy; a reference-only artifact is not a backup. Never place credentials in logs/metadata.

### Suggested project layout

```text
simulation/
  simulate.py
  README.md
  requirements.txt
  swss.toml                     # when using companion configuration; parameters optional
  logs/                         # optional convenience mirror
  outputs/
    run_20261018T123000Z_RUNID/
      logs/run_20261018T123000Z_v0.1.1_RUNID.log
      summary.json
      measurements.csv
      artifacts/                # optional exports in documented formats
      checkpoint.npz            # only if restart is implemented
```

`RUNID` stands for a collision-resistant ID; filenames identify purpose and run identity. File timestamps do not replace solver time. JSON/CSV are recommended independent evidence, not mandatory filenames. When automatic capture is claimed, the effective output folder is the capture source. A second logging handler MAY mirror the same log beside the entry point; mirrors SHOULD have documented retention/rotation that preserves active-run and required research evidence. Exclude generated logs/outputs, environments, caches and large artifacts from source snapshots/Git as appropriate; retain research source and relevant small text evidence.

All launchers and editors MUST preserve one ordered argv list, including aliases, numeric spellings, explicit empty strings, repeats and delimiters, until an explicit user edit. Record the exact launched vector separately from resolved scientific values. The detailed editing rules in §4.3 apply whenever typed editing is offered. Shell strings are not a substitute for the recorded vector.

## 3. Independent optional capabilities

These capabilities define observable obligations, not application APIs, environment variable names, UI controls or serialized telemetry formats. Implementers MUST document the transport, format/version and adapter used; consumers verify behavior using §5. A local adapter cannot redefine these obligations.

### 3.1 Coordinated run capture

A cooperating launcher and simulation MUST agree on one unique effective run output root before writing. The adapter MUST document how the root is supplied and acknowledged. The script MUST use that root directly, without allocating another run root beneath it; artifact subdirectories are permitted. Explicit output arguments MUST resolve to the same root or fail clearly before writing. Standalone execution MUST still allocate a unique root with documented explicit-path precedence. Successive and simultaneous runs MUST use distinct, non-overlapping roots. Allocation alone does not redirect arbitrary script writes.

The recorder MUST automatically preserve the timestamped `.log` from the effective run root, without a post-run manual upload, and record process stdout/stderr separately. The adapter MUST document capture selection, ordering/precedence, file and run budgets, retention and finalization timing. Required logs MUST be copied or durably stored, not merely referenced. Required evidence outside the watched root, missing, skipped, oversized or interrupted captures MUST be reported as incomplete independently of solver success. Test actual bytes after closure; size/mtime alone cannot prove unchanged content. Capture MUST NOT follow symlinks outside the root.

Capture provenance MUST distinguish copied artifacts from references, record artifact paths and run identity, and expose capture outcomes. Small text evidence SHOULD be copied; large binaries MAY be referenced with independent verified backups. Source snapshots MUST exclude generated output trees, including earlier sibling runs, while retaining research source and applicable companion configuration. Snapshots record selected bytes at a stated time; they do not isolate a running process from later edits. Git archival, cloud upload or other data transfer requires separate authorization. A source-adjacent log mirror MAY be retained but does not substitute for captured evidence.

### 3.2 Progress and metrics

Finite jobs MUST report truthful measured progress; indeterminate jobs MUST use stage descriptions without fabricated percentages. Implementers MUST document the selected structured or text adapter, current/total interpretation and compatibility requirements. Implementers SHOULD rate-limit reporting and measure overhead. Steps, solver time, process exit status and capture completion are distinct. A display synthesized on process exit MUST be labeled separately from the last actual progress report; 100% is not proof of successful computation.

Scientifically meaningful metrics SHOULD be emitted and independently saved in text evidence. Every metric MUST satisfy §2 diagnostic requirements: formula, units, sampled solver time, source-state values and explicit nonfinite handling. Do not infer arbitrary log numbers as measurements or substitute interpolation for solver samples. A simulation with no appropriate metric MUST document why. A recorder MUST expose rejected/dropped measurements and retention limits; errors must not be silently converted into valid observations.

### 3.3 Scientific export

SWSS defines **no binary wire format**, file extension, geometry API or universal restart container. Authors MUST identify the chosen format/version and matching reader, document supported quantities, geometry, dtypes, coordinate transformations, centering, units, channels and identity semantics, and retain enough evidence to verify them. Unknown units stay unknown. Do not fabricate persistent identity from row order or silently normalize/narrow values for display. Represent complex quantities through documented components when needed and retain independent full scientific state.

Each artifact MUST use a new unused full path. Names SHOULD combine simulation/case, UTC timestamp and collision-resistant run ID generated independently of the scientific RNG. The same ID MUST correlate logs, artifacts and metadata; multiple artifacts require distinct labels or sequence suffixes. Unique directories may supply full-path uniqueness but the mapping MUST be recorded. Exclusive creation or an equivalent atomic no-replace operation MUST protect against concurrent collisions; an existence check alone is insufficient. An explicit occupied path MUST fail without modifying existing bytes or silently selecting another path. An alternative requires documented explicit opt-in and recording the actual destination. Report collisions distinctly from permissions, missing parents or exhausted storage.

Export cadence MUST be independent of solver timestep and MUST NOT change numerical state or RNG calls. Finalize writers, preserve partial evidence on failure, and document whether the solver stops or continues. After an I/O failure, do not resume writing to that artifact without a format-defined, separately validated recovery mechanism; otherwise retain the safe prefix and use a new destination. An incomplete prefix MUST NOT be labeled a complete or verified run.

Before describing an artifact as verified, read actual payloads through the matching reader and compare values/dtypes, geometry, timestamps, units, channels and applicable identity histories against source samples. Record validation coverage and integrity checks; viewing alone is not payload verification. If intended for visualization, inspect a representative short artifact in a compatible viewer as an additional check. Export enabled/disabled runs MUST preserve the scientific baseline and RNG behavior. Visualization artifacts are not restart checkpoints unless they separately contain and validate all required solver state and lineage.

## 4. Optional portable configuration and parameters

### 4.1 Location, association and adoption

Participating simulations MUST use **one `swss.toml` at the simulation root**, containing a reserved `[swss]` section and optional `[extensions.<identifier>]` tables. A Python simulation plus this one companion file MUST suffice for these declarations and optional extension data; no second TOML file or generated shadow configuration is required. A root is an explicitly selected project directory, not one guessed by walking parents. One document describes one simulation entrypoint. Multi-entrypoint project orchestration is outside this capability; no recursive discovery, includes, overlays or file merging is permitted.

The only portable discovery path is `swss.toml` directly beneath that root. Its `swss.entrypoint` MUST exactly match the selected launch entrypoint's normalized root-relative path. A mismatch disables typed use with an explanation; it never changes the selected program. The portable section MUST NOT select an interpreter, shell, executable, working directory or environment. Extension data is not executed or interpreted by portable metadata discovery.

A missing `swss.toml` means no portable metadata is available. Baseline simulations need no companion file unless adopting this capability. Parameter rows MAY be omitted. An adopting tool needing configuration for a new run reports that requirement; it does not search for alternate files or convert history. Manual argv remains available subject to independent launch checks. Discovery MUST NOT write configuration or scientific source.

The companion-file path and portable entrypoint/source-manifest paths MUST use `/` separators and relative components, excluding empty components, `.`, `..`, leading `/`, backslashes, drive/URI prefixes and control characters. Resolve within the selected root; reject symlinks in the candidate or any referenced path component, escapes, non-regular files and inaccessible paths. Do not expand `~`, environment variables or globs. A selected root itself may be canonicalized once with user knowledge; all checks then use that root. Recheck identity when reading to avoid a check/open substitution; if a consumer cannot establish safe access, it MUST decline metadata use, not weaken containment.

Discovery and argv precedence:

1. **Existing/manual argv remains authoritative user intent.** Discovery never overwrites tokens, even when declarations change.
2. A valid `swss.toml` supplies portable parameter metadata. Consumers MUST NOT merge it with other configuration files, legacy JSON declarations or static discoveries. No alternative metadata file is required by this contract.
3. Absent, invalid, stale or unsupported metadata yields a visible diagnostic and manual fallback, without silently switching to another source. An application MAY separately offer explicitly selected, bounded static discovery; it MUST identify that source, preserve argv and not present it as the SWSS declaration. No static discovery implementation is required here.

Missing/invalid `[swss]`, entrypoint mismatch and unsupported schema versions disable typed use. A valid partial declaration remains the selected source: undeclared and unsupported options stay manual, rather than being silently supplemented from AST discovery. Duplicate keys are parse errors; duplicate parameter IDs or alias ownership are document-wide ambiguity errors, not last-wins rules. Independent application safety/configuration checks may still prevent launch; manual fallback is not a bypass for them.

### 4.2 Data schema

Use UTF-8 **TOML 1.0.0** syntax. Consumers MUST reject duplicate keys and invalid TOML, and accept only the following schema. TOML syntax is defined by the [TOML specification](https://toml.io/en/v1.0.0); all parameter semantics and limits are stated here. Only root tables `swss` and optional `extensions` are allowed. Unknown fields or structures within `swss` invalidate portable metadata use; extension fields are handled separately below. New schema versions require explicit consumer support, not best-effort reinterpretation.

| Field within `[swss]` | Requirement |
| --- | --- |
| `schema_version` | Required integer `2`, not a boolean or string. |
| `entrypoint` | Required root-relative regular-file path, bound to the selected entrypoint. |
| `simulation_version` | Required nonempty string identifying the declared simulation source revision; distinct from the schema version and SWSS revision. |
| `parameters` | Optional array of parameter tables; zero through 128 entries. Omitted or empty means no typed declarations, not no CLI arguments. Manual argv remains usable; this is not a schema error. |
| `source_files` | Optional array of `{path, sha256}` tables, unique paths. Each hash is 64 lowercase hexadecimal characters over exact file bytes. If present, include the entrypoint. No other fields. |

`[[swss.parameters]]` contains the parameter rows below; optional `[[swss.source_files]]` contains bindings. A third-party consumer MUST be able to use these tables without installing or consulting any application. `swss.schema_version` versions only the portable section, not extension schemas.

`extensions` MUST be a table of tables keyed by stable lowercase ASCII identifiers matching `[a-z][a-z0-9_-]{0,63}`. No extension is mandatory or defines a baseline capability. Portable readers MUST ignore extension semantics while enforcing whole-file syntax and resource limits. They MUST NOT execute extension data, dereference its paths, import code or treat it as portable defaults, identity, bindings or argv. An extension-aware consumer MUST document its identifier, versioning and semantics; unknown or unsupported extensions MUST NOT invalidate otherwise valid portable metadata. Such a consumer may decline its own optional feature with a diagnostic. No extension overrides `swss`; conflicting duplicates MUST be rejected by the interpreting consumer, not resolved by precedence. Portable readers need not understand them.

Extensions are for local optional details only. A shared portable workflow addition MUST first be specified and reviewed here, with an explicit schema/revision compatibility decision, before implementation elsewhere. No particular extension schema is standardized in this revision. Do not store credentials in source-captured configuration.

Each parameter requires `id`, `kind`, `required`, `type`, `action`, `help`; `options` or `name` depends on kind. Optional fields are `choices`, `default`, `repeatable` (boolean, defaults to false). No implicit `required`, `type` or `action` is inferred.

| Parameter field | Meaning and constraints |
| --- | --- |
| `id` | Stable within the entrypoint across revisions; ASCII `[a-z][a-z0-9_]{0,63}`. It is not a CLI token or Python destination. A changed scientific meaning SHOULD receive a new ID; renaming never migrates argv automatically. |
| `kind` | `option` or `positional`. |
| `options` | For options only: 1–8 exact case-sensitive aliases, no duplicates. Each matches `--[A-Za-z][A-Za-z0-9_-]*` or `-[A-Za-z]`. First alias is the preferred new-control spelling, never a replacement for saved aliases. `--`, embedded `=`, whitespace, short bundles and abbreviations are not aliases. |
| `name` | For positionals only: a descriptive ASCII identifier using the same grammar as `id`. It is a label, never emitted as a token. |
| `required` | Boolean: whether the parser requires presence, not whether a default hint exists. A supported value option always takes exactly one value when present, even if `required = false`. |
| `type` | `integer`, `float`, `string` or `boolean`. Booleans are no-value flags, not value-taking `true`/`false` options. |
| `action` | `store` for integer/float/string options; `store_true` or `store_false` for boolean options. Positionals use `store` and a non-boolean type but are manual-only. |
| `help` | Human-readable description, plain text; empty allowed, never interpreted as markup, templates or commands. |
| `choices` | Optional nonempty array of at most 100 distinct values of the declared type. Not supported for flags. An explicitly supplied default must be a member. |
| `default` | Optional scalar of the declared type, informational only. Absence means unknown; `default = ""` is a known empty-string hint. TOML has no null value: do not invent a sentinel for `None`. |
| `repeatable` | True marks the row manual-only. No append/count/collection serialization is specified. |

Integer hints/choices MUST be TOML integers in signed 64-bit range, excluding booleans. Float hints/choices MUST be finite TOML floats, excluding integers and booleans; use binary64 numeric equality for duplicate/membership checks (`-0.0` equals `0.0`). String hints/choices MUST be TOML strings. Flags permit only boolean defaults. A default need not equal the usual argparse implicit default, since parsers can override defaults; it never determines token presence.

For supported value controls, validate integer text against `[+-]?[0-9]+` and signed 64-bit range, and float text against `[+-]?(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)(?:[eE][+-]?[0-9]+)?` with a finite binary64 result. This is a deliberately narrow portable editing subset, not a claim about every parser's grammar. Preserve the original text after validation: `00192`, `+192`, `1e-3` and `0.001` are not interchangeable argv spellings. Choices compare parsed numeric values or exact string values; display labels cannot replace tokens. Other numeric forms remain possible through manual editing, subject to the script's parser.

Positionals, repeated occurrences, `repeatable = true`, unsupported type/action combinations, unknown row fields (such as `nargs`), or otherwise invalid individual rows (except document-wide errors specified below and safety-limit failures in §4.5) MUST be labeled manual-only with a reason. Do not partially interpret that row. Other valid rows MAY remain typed. Missing/invalid IDs or option alias lists, duplicate IDs, or aliases claimed by different rows invalidate the whole document because ownership is ambiguous. A syntactically valid but unsupported action such as `append` may retain its unique ID/aliases for diagnostics only. Mutually exclusive groups, paired boolean actions sharing a destination, subcommands, custom converters and multiple-value options have no typed semantics in schema 2 and MUST use manual handling; authors MUST NOT misdeclare them as independent scalar controls.

**Parameter help authoring guidance (non-normative)**

Parameter descriptions SHOULD concisely explain the parameter's purpose, its effect on simulation behavior, relevant units and important constraints where applicable. Descriptions SHOULD avoid repeating information already represented by structured metadata, including parameter names, data types, choices and default values.

Descriptions SHOULD generally fit within **256 UTF-8 bytes**. Longer explanations MAY be used when scientifically justified. This is an authoring recommendation, not a validation limit: otherwise valid descriptions exceeding 256 bytes remain valid up to the existing **4,096 UTF-8-byte hard maximum** in [§4.5](#45-safety-and-bounds). Exceeding the recommendation is not grounds for truncating help or rejecting metadata.

Empty help remains allowed. This guidance changes no plain-text, parsing, control-character, safety-limit or manual fallback rules and does not prescribe consumer UI layout.

### 4.3 Exact argv contract

A consumer MUST maintain one ordered list of argument strings, independent of presentation groups. Opening, rescanning, changing source, saving/reloading or changing metadata MUST preserve existing tokens byte-for-byte in their UTF-8 representation and in the same order. Do not insert defaults, resolve aliases, deduplicate repeats, combine/split tokens, normalize numbers, expand variables or execute a shell. Only explicit user edits may change tokens; show the resulting exact argv before launch.

- Supported long `--name=value` splits at the first `=` only for presentation; preserve the original form on save. Separate `--name`, `value` and short `-n`, `value` forms remain separate. No inference for short attached values or bundles. Values may contain further `=` characters.
- A flag control means **emit this option**, not set the resulting scientific value. Enabled `store_true` emits only its alias (parser sets true); enabled `store_false` emits only its alias (parser sets false). Disabled emits nothing. Do not fabricate opposite flags, `false`, empty values or defaults. Required flags still need deliberate inclusion.
- Absence, a token with no following value, and an explicit empty string are distinct. For example `[]`, `["--label"]`, `["--label", ""]` and `["--label="]` MUST remain distinct representations. A supported string control can explicitly request an empty string; a blank manual value field MUST NOT silently add one. A missing value for a known scalar is a diagnostic, not authority to repair argv.
- Tokens after the first standalone `--` are manual positional content, even if they look like options. Unknown tokens, repetitions and ambiguous token/value pairings MUST stay manual and retain order. When pairing would consume a known option token as a value or has uncertain ownership, decline typed mapping; do not guess missing values. A negative numeric token matching the declared grammar may be a separate numeric value.
- On explicit edits to an unambiguous existing row, replace/remove only that row's identified token span in place. Newly enabled options MUST be inserted at a user-visible, confirmed position (default: immediately before `--`, otherwise at the end), without moving existing tokens. Use the first alias unless the user selects another; new long scalar options use `--name=value`, new short ones use two tokens. New flags use one token. Choice selection MUST preview the exact token text before acceptance, including any consumer-generated numeric spelling.

Metadata validation MAY prevent a typed edit from being accepted until corrected. It MUST NOT strand otherwise usable manual argv: offer explicit manual editing without metadata-based launch rejection, subject to the runner's independent safety/launch checks. The simulation may still reject those arguments. Never downgrade a known validation error silently or claim manual mode validates it.

### 4.4 Consistency and provenance

Authors MUST maintain declarations alongside source and bump the simulation source revision under their claimed SWSS versioning policy when changing this source-package metadata. `simulation_version` labels the revision the declaration describes; it is not an automatic version bump. Store declarations with captured source when used. Consumer writes to simulation files or automatic synchronization are not authorized by discovery.

Source manifests are optional: basic typed controls MUST work without them, with **binding unverified** shown. If `swss.source_files` is provided, consumers MUST hash the listed files as data and compare each entry before enabling typed use. A missing file, unsafe path or mismatched digest makes the binding stale/invalid and disables typed use. A declared version mismatch against a separately available, safely obtained simulation version also disables typed use; never import source to obtain it. Without hashes or a comparable version, display **binding unverified**, not **current**. Matching hashes prove only listed bytes match, not runtime semantics or completeness of a source package. Imported modules, dependencies and environment changes can invalidate behavior even with a matching entrypoint.

On rescan or before launch, recheck the whole companion-file bytes and any supplied bindings. Changes MUST invalidate the previous metadata-based preview, preserve argv and require review before reusing typed controls. A source change after the check remains possible; disclose the check's timing and do not claim isolation. Oversized source hashing is **binding unverified / manual-only**, not permission to skip a supplied binding and label it verified.

When declarations are used to configure a recorded run, consumers MUST retain the root-relative declaration path, exact companion-file bytes and SHA-256 (including extension sections), portable schema version, declared simulation version, selected entrypoint, selected discovery source, binding status/reasons and checked source hashes (if any), plus the final exact argv. Runtime resolved parameters remain separate scientific provenance. If a declaration later becomes invalid or is bypassed, retain its last-used provenance and the bypass/review decision; a new manual run need not invent metadata. Do not record absolute workstation paths or credentials solely for this convention. Consumers must use their existing safe provenance storage; this specification mandates no database schema or migration.

### 4.5 Safety and bounds

Discovery MUST parse data only: no imports, evaluation, `--help`, subprocesses, plugins, command interpolation, network fetches or dependency installation. Render descriptions as text. Declaration values do not authorize file writes or select executable code.

Interoperable limits (exceeding any is a visible document failure with manual fallback): File bytes, depth, total entries and string bounds apply to the entire mixed-use file, including ignored extension tables; parameter-specific limits apply within `swss`: **262,144 bytes** per document; nesting depth **8** (root table depth 1; each contained array/table adds 1); **4,096 total keys and array elements** (count each table key and each array slot once, including nested containers; keys also obey string bounds); **128 parameter rows**; **8 aliases per row**; **100 choices per row**; **32 source files**; **4,096 UTF-8 bytes per string**, except **1,024 per path** and **128 per alias**. Strings MUST exclude NUL and control characters U+0000–U+001F/U+007F, except LF/tab in portable `help` and extension text values (never keys). Nonfinite numeric values invalidate the document. Within `swss`, dates/times and nested values outside specified structures invalidate portable metadata. Within extension tables, TOML data types and nested tables/arrays are allowed within the whole-file bounds; portable consumers do not apply extension schemas or dereference extension paths. Scalar row type errors use the manual-row rule in §4.2; safety/count/string-limit failures invalidate the document.

Consumers MUST bound parsing work/memory as well as input bytes; reject excessive nesting before allocating unbounded structures (a bounded parser or isolated resource-limited parse is acceptable). Source hashing is streaming, limited to **16 MiB per file / 64 MiB total**. Consumers with tighter local limits MUST disclose them and fall back manually rather than claim full schema-2 support for all valid inputs. No AST parsing is required; source exceeding hash limits cannot use a supplied verified binding in this revision. Manual argv remains available regardless of discovery failure, subject to independent runner safety constraints.

### 4.6 Examples

This single `swss.toml` example contains portable parameter declarations. It intentionally omits source hashes: its binding is unverified, but its typed controls remain usable. It is illustrative and makes no claim about any scientific solver's defaults. A real author must choose and validate the values against their parser.

```toml
[swss]
schema_version = 2
entrypoint = "simulate.py"
simulation_version = "0.1.1"

[[swss.parameters]]
id = "grid_size"
kind = "option"
options = ["--N", "-n"]
required = false
type = "integer"
action = "store"
help = "Grid resolution along each axis"
default = 192

[[swss.parameters]]
id = "timestep"
kind = "option"
options = ["--dt"]
required = true
type = "float"
action = "store"
help = "Time advanced per integration step, in model time units"

[[swss.parameters]]
id = "precision"
kind = "option"
options = ["--precision"]
required = false
type = "string"
action = "store"
help = "Arithmetic precision"
choices = ["single", "double"]
default = "double"

[[swss.parameters]]
id = "export"
kind = "option"
options = ["--export"]
required = false
type = "boolean"
action = "store_true"
help = "Write visualization output"
default = false

[[swss.parameters]]
id = "plots"
kind = "option"
options = ["--no-plots"]
required = false
type = "boolean"
action = "store_false"
help = "Disable plots"
default = true

[[swss.parameters]]
id = "label"
kind = "option"
options = ["--label"]
required = false
type = "string"
action = "store"
help = "Optional annotation"
default = ""

```

A minimal companion file with no parameter declarations is valid:

```toml
[swss]
schema_version = 2
entrypoint = "simulate.py"
simulation_version = "0.1.1"
```

No extension is needed. To demonstrate optional opaque data in the same file, the valid extension variant appends this table (its note has no portable semantics):

```toml
[extensions.annotation]
note = "Local display note only"
```

These rows correspond, respectively, to ordinary argparse declarations with `type=int`, `type=float, required=True`, `choices=["single", "double"]`, `action="store_true"`, `action="store_false"`, and `type=str`. The declared defaults must be supplied to the parser where applicable; the metadata does not supply them. No source code is executed to discover these rows. A declaration may describe another CLI implementation with the same behavior.

Intentional malformed fixture (not a valid configuration): duplicate portable key; consumers MUST reject the whole document:

```toml
[swss]
schema_version = 2
schema_version = 3
```

Ambiguous example mutation: append a copy of `grid_size` with a new ID but the same `--N` alias; reject the entire document. Unsupported-row mutation: add `nargs = "+"` to `grid_size`; mark that entire row manual-only, keep other valid rows. Unsafe mutation: set `swss.entrypoint` to `"../outside.py"`; reject before reading that path. Unknown default: omit `default`; `default = null` is invalid TOML, while `default = "null"` is a literal string and invalid for a numeric row.

## 5. Conformance and evidence

A conformance report MUST identify SWSS revision, claimed baseline/capabilities, simulation and tool versions, environment, fixture inputs, expected and observed results, retained evidence, deviations and untested paths. A failed MUST prevents the corresponding claim; untested behavior is not a pass. A documentation review or syntax parser is not a consumer or scientific conformance test.

### 5.1 Baseline and capability cases

| Case | Required observation |
| --- | --- |
| Source/configuration change before recorded run; unchanged source with different argv | Bump source revision for the former, not the latter; retain exact source identity independently of labels. |
| Successful short job, intentional failure, handled cancellation | Truthful status/exit codes, timestamped logs, closed files where possible, partial-evidence reasons; no incomplete output described as verified. |
| Two successive and two simultaneous runs | Distinct output roots and artifact paths; prior bytes unchanged; consistent run IDs in log and provenance. |
| Existing explicit artifact path; concurrent creation race | Atomic refusal without overwrite or silent rename; distinguish other I/O failures. |
| Instrumentation/export enabled versus disabled | Compare scientific values and RNG behavior against an approved baseline; report tolerances and coverage. |
| Coordinated output root plus conflicting explicit output | Use agreed root directly or reject before writing; actual capture target agrees; no nested replacement run root. |
| Required log missing, outside root, oversized or capture interrupted | Automatic copied log on success with no manual upload; separate incomplete capture status on each failure; process streams retained separately. |
| Source snapshot with output siblings and local log mirror | Generated output trees excluded; source/config retained; mirror not mistaken for captured evidence. |
| Finite/indeterminate progress; nonfinite/dropped metric | Truthful stages/counts, no fabricated completion; explicit diagnostic and independent numerical comparison with units/time. |
| Export payload and representative viewer check where applicable | Matching reader compares values, dtypes, geometry, timestamps, units, channels and identity history; viewing alone never passes integrity. |
| Export failure or partial artifact | Preserve partial evidence and independent scientific archives; documented solver policy; no unvalidated writer recovery. |
| Referenced large artifact and source backup | Demonstrate independent restoration or report backup unverified; references alone do not pass. |
| Adoption of new reader | Complete configuration/launch/capture/discovery paths tested before retirement/release; old records, snapshots, argv and artifact bytes unchanged. |

### 5.2 Portable metadata cases

Start from the six-row example in §4.6 and a harmless matching entrypoint. These are required consumer cases, not claims of an implemented reference parser. Mutations define input and expected outcome.

| Fixture | Required result |
| --- | --- |
| Valid six-row file with no argv | Six typed rows; no default tokens inserted; missing required `--dt` diagnostic with manual escape; binding unverified. |
| Minimal file; variant `parameters = []` inside `[swss]` | Valid metadata, zero typed rows; manual argv remains available. |
| Optional `extensions.annotation` appended; unknown extension version | Same portable result, no semantic interpretation or required extension installation. |
| Root `apps` table, unknown portable header field, schema 1 or 3 | Unsupported document diagnostic, preserved argv and manual fallback; no automatic conversion. |
| Exact argv `['--N', '00192', '--dt=1e-3', '--label', '', '--unknown', '--', '--export']` | Byte-for-byte ordered round trip through open/rescan/save/reload; unknown and post-delimiter content manual. |
| `--label=a=b`, `--label=`, `--label` without value | Split first equals only for display; retain explicit empty; diagnose missing without repair. |
| Enable/disable each boolean flag | One exact option token when enabled, none when disabled; no opposite token or invented value. |
| Repeats/aliases, positional, short bundle, uncertain pairing | Manual handling without moving or normalizing any token. |
| `repeatable=true`, `action="append"`, unknown row `nargs`, wrong scalar type | Whole affected row manual-only with reason; other valid rows retained. |
| Numeric/string choices, wrong default type, duplicate choices, default outside choices | Enforce §4.2; invalid row manual-only. Signed-64-bit integers and finite binary64 values checked, booleans never numeric defaults. |
| Duplicate TOML key, duplicate ID/alias, missing/invalid ID or option aliases | Whole-document failure; no last-wins or inferred ownership. |
| Partial declaration omits precision; other metadata disagrees | Only declared valid rows typed; no static merge or source switch. |
| Missing `swss.toml`, unrelated TOML present | Missing-metadata diagnostic; no substitute search, recursive discovery or shadow file. |
| Modified companion bytes, including extension-only edit | Invalidate preview, preserve argv/provenance and require review before typed reuse. |
| Declared version mismatch, changed/missing bound source | Disable typed use; retain evidence and explicit manual bypass decision. |
| Listed hashes match but unlisted module changed | Report only listed-byte binding, never complete semantic equivalence. |
| Absolute/traversal/symlink/URI path, entrypoint mismatch, open-time substitution | Refuse unsafe association; never change selected program or weaken containment. |
| File 262,145 bytes, depth 9, 4,097 entries, 129 rows, 9 aliases, 101 choices, 33 sources | Reject each limit violation with manual fallback; also test exact permitted boundaries. |
| Oversized strings/paths/aliases; hashing above 16 MiB per file or 64 MiB total | Apply §4.5 bounds; never silently skip supplied bindings and claim verification. |
| Malformed/deep/oversized ignored extension | Whole-file failure; ignoring semantics never bypasses syntax/safety bounds. |
| Invalid UTF-8, NUL, nonfinite float, portable date/time | Whole-document failure; no execution side effects. |
| Shell syntax in help/string | Display as text; never interpolate or execute. |
| Declaration changes between safe open and preview/launch | Detect changes at checks, refuse stale reuse, disclose post-check race limits. |

Discovery tests MUST assert no source imports, subprocesses, network requests or filesystem writes. Provenance MUST retain the exact declaration used, not a later version. Test an explicit manual path through each metadata failure, subject to independent runner safety checks. Consumer-local tighter limits MUST be disclosed and cannot claim complete schema-2 support.

## 6. Specification-first development

Portable additions to configuration or shared workflow contracts MUST be proposed and reviewed in this repository first, with requirements, compatibility impact and conformance cases. Only then implement the accepted contract in adopting repositories under their own authorization. Consumer-specific details may remain local extensions or implementation details but MUST NOT silently alter SWSS semantics. Adoption is voluntary. Owner review of this repository does not authorize external implementation, merge, release, publication or certification.

The [review checklist](../../docs/REVIEW.md) records evidence expectations. First reference implementation, consumer adapters and scientific pilots remain future work. No external tool or simulation is claimed to support or conform to this revision.
