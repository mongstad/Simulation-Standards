# Scientific Workflow Simulation Standard (SWSS) v1.0

**Status:** Draft for owner review, 2026-10-18. **Audience:** Python scientific simulation authors.

SWSS is a voluntary, independent workflow convention, not an industry certification, new scientific data format, or a dependency requirement on either application. **MUST** is required for the profile claimed; **SHOULD** is recommended with documented exceptions; **MAY** is optional.

## 1. Independent profiles

| Profile | Requirements |
| --- | --- |
| **Core** | General versioning, logs, provenance, isolated outputs, truthful lifecycle |
| **SimShelf** | Core plus SimShelf recorder compatibility, progress, metrics and automatic capture |
| **Wavez** | Core plus verified Wavez WVZ1 scene recording |
| **Full** | Core plus both optional profiles |

A project MUST identify which profiles it claims, tested tool versions and deviations. SimShelf and Wavez remain independent products; users may adopt either or neither. Existing simulations are modernized one by one only when selected for future runs. SWSS is maintained and versioned independently in this repository. Its normative requirements and expected simulation-side behavior are stated here; Core can be used without either application or its documentation. Application repositories own their APIs, formats and implementation guidance. Links to them support integration, do not replace SWSS requirements, and do not automatically revise SWSS when an application changes. Record tested versions and resolve compatibility mismatches explicitly rather than silently changing a claimed SWSS requirement.

## 2. Core profile: scientific integrity

1. Integrating workflow features MUST NOT silently change numerical equations, timestep, grid, precision, RNG stream, boundary conditions or other scientific behavior. Preserve a before/after reference or explicitly document the approved scientific difference.
2. Each run MUST document all experiment parameters and resolved runtime values. Record simulation name, start time, model version, selected Python version, actual arguments, solver configuration (including timestep and boundary conditions), grid extent/resolution, time units, channel/coordinate units, output cadence and random-seed/state policy. SHOULD record dependency versions, GPU/backend/precision, numerical assumptions, source identity, external input hashes and restart lineage. Disclose reproduction limits from floating-point backends, parallel scheduling, dependencies and external inputs. A `summary.json`, when produced, MUST distinguish physically modeled, diagnostic and dimensionless quantities.
3. Source versioning follows MAJOR.MINOR.PATCH. Any accepted modification to the simulation source package (including comments, configuration and logging/export/instrumentation behavior) MUST bump the declared version before the next recorded run. Breaking scientific changes normally use major; substantive scientific revisions minor; corrections/instrumentation patch. Runtime argument differences alone do not bump the source version. Capture exact source bytes/hash independently: matching labels do not guarantee identical code, and matching structural fingerprints do not prove identical behavior. SHOULD warn/block in CI if tracked code changes without version bump; this is a proposed SWSS development gate, not a built-in SimShelf auto-bump or enforcement feature. Checks MUST NOT automatically edit research source.
4. Every run MUST write a uniquely named, timestamped, human-readable `.log` file including version, parameters, status and useful errors/tracebacks. UTC timestamp format SHOULD be YYYYMMDDTHHMMSSZ with an additional collision-resistant run ID. Flush/close on normal shutdown and handled failure; forced termination can leave partial evidence. Avoid uncontrolled per-cell progress writes.
5. Each run MUST have a unique output directory, including concurrent runs, and MUST NOT silently overwrite historical output. File paths, parameter conventions, inputs and outputs must be documented.
6. Failure MUST use a nonzero exit code. Incomplete outputs MUST NOT be labeled verified complete. Close text logs, measurement files and any visualization writers on normal completion; on handled failure/interruption, SHOULD close them safely and record the reason while preserving partial evidence. Keep visualization recording and diagnostic/checkpoint cadences independent of the solver integration step. Restart checkpoints MAY be provided but MUST contain the solver state actually needed to resume, with provenance and restart lineage. Wavez scenes are not restart checkpoints.
7. SHOULD provide at least one scientifically meaningful numeric diagnostic where appropriate; otherwise MUST document why none applies. Reported diagnostics MUST use consistent names, documented formulas and units (or explicit dimensionless/unknown units), and actual sampled solver timestamps. MUST compute them from source solver state, distinguish measurements from estimates or visual interpolation, and handle nonfinite outcomes explicitly without disguising errors. A numerical measurement is not an image-derived impression.
8. Large binary results SHOULD remain outside Git history by default and have their own backup strategy; a reference-only artifact is not a backup. Never place credentials in logs/metadata.

### Suggested project layout

```text
simulation/
  simulate.py
  README.md
  requirements.txt
  simshelf.toml                 # SimShelf profile only
  logs/                         # optional convenience mirror
  outputs/
    run_20261018T123000Z_RUNID/
      logs/run_20261018T123000Z_v0.1.1_RUNID.log
      summary.json
      measurements.csv
      simulation_case_20261018T123000Z_RUNID.wvz  # Wavez profile only
      checkpoint.npz            # only if restart is implemented
```

`RUNID` stands for a collision-resistant ID; filenames identify purpose and run identity. File timestamps do not replace solver time. JSON/CSV are recommended independent evidence, not mandatory filenames. Each run's effective output folder is the SimShelf capture source when that profile is used. A second logging handler MAY mirror the same log beside the entry point; mirrors SHOULD have documented retention/rotation that preserves active-run and required research evidence. Exclude generated logs/outputs, environments, caches and large artifacts from source snapshots/Git as appropriate; retain research source and relevant small text evidence.

## 3. Optional SimShelf profile

The simulation MUST be registerable with a stable Python entry point and appropriate simshelf.toml. Declare a literal `SIMSHELF_VERSION` assignment in the configured `version_file`, and include that file in source capture. This is the simulation revision label, not the SimShelf build or WVZ1 format version. Requiring it and bumping it for every accepted source change are SWSS house rules: SimShelf itself allows unversioned runs and owner-chosen version changes. The human label, exact selected source snapshot and structural fingerprint are distinct. Snapshots record startup bytes and do not isolate a running process from later source edits. Prefer statically discoverable argparse declarations or a separately validated simshelf-arguments.json schema. Discovery is advisory: validate actual accepted arguments and resolved defaults against the script.

### Coordinated run output folders

SimShelf defaults to **Fixed folder (existing behavior)**. The opt-in **Unique subfolder for each run** policy allocates the actual run folder beneath the configured capture parent when the run starts. `SIMSHELF_OUTPUT_DIR` and joined `run.output_dir` identify that same allocated folder. Selecting this policy does not make a non-cooperating script safe, migrate old outputs or redirect writes. The [SimShelf running guide](https://github.com/mongstad/SimShelf/blob/main/docs/RUNNING.md#unique-output-folders-for-cooperating-scripts) explains application controls; the SWSS requirements for the simulation are:

- The script MUST use the supplied folder as its effective run output root and write capturable logs, CSV/JSON, scientific snapshots and optional WVZ1 artifacts beneath it. It MUST NOT append another run directory to establish a separate run root. Artifact subdirectories such as `logs/` remain appropriate. The allocated folder already exists; `mkdir(parents=True, exist_ok=True)` is appropriate when ensuring it exists.
- Explicit simulation `--output` / `--output-dir` arguments MUST NOT silently override the coordinated location. The script MUST either resolve them to that same folder or reject a conflict clearly before writing. SimShelf does not rewrite arguments, expand environment variables inside them or redirect arbitrary file writes. Required artifacts written elsewhere MUST be reported as missing from capture, not assumed preserved.
- Without a recorder-supplied folder, standalone execution MUST deliberately choose a unique output directory, with documented and tested explicit-path precedence. In **Fixed folder** mode, the recorder and script still MUST be configured to use the same unique target for each run. The application's fixed default does not waive Core's isolation rule. Successive and concurrent runs MUST have distinct, non-overlapping output roots, and retain Core's unique run identity and truthful success/failure evidence.

Capture rules and copy/reference budgets are evaluated relative to the allocated run folder. The entire configured parent remains excluded from source snapshots, including earlier sibling runs. Optional Git archival requires separate consent; selecting the output policy does not authorize it. Referenced/original binary artifacts still need independent backups, and Git archival is not a replacement for those backups.

For adoption, select the opt-in policy only after checking the script's output resolution. At run start, use the supplied root directly, then confirm the recorded capture path and actual artifact paths agree. Verify successive and simultaneous runs preserve earlier originals; inspect missing/skipped artifacts separately from solver completion. Wavez export remains optional and follows §4 when claimed.

### Automatic capture and telemetry

**Automatic log capture is required with no post-run upload:** write a timestamped real .log file directly to the effective output folder's logs/ subdirectory. In SimShelf file-capture settings, place a `copy` rule matching `**/*.log` before any broader matching rule, and verify file/run size budgets. For successful capture validation, SimShelf MUST automatically show that log in the run's Files record after final capture. Native recorded process stdout/stderr MUST also be available in Logs, subject to recorder retention limits; it does not replace the timestamped file. A second logging handler MAY also create a local mirror next to simulate.py; source-adjacent logs alone are NOT automatically ingested by current output-directory capture. Avoid symlinks. Verify normal, failed and cancelled runs and inspect skipped/oversized artifacts. Capture validation MUST report missing/skipped/oversized required logs as incomplete, separately from solver success. File capture may remain incomplete after interrupted processes.

For example, add this rule to the project's existing `simshelf.toml` **before any broader matching rule**, and confirm the effective File capture settings used by the next run:

```toml
[[capture.rules]]
pattern = "**/*.log"
action = "copy"
```

This fragment does not configure a unique output directory or size budgets; those must also be set and verified. Default capture limits are 25 MB per file and 200 MB per run, not a promise to retain every log. Final capture inventories new/changed files by size and modification time, excludes symlinks, and can miss rewrites that preserve both. Unique run paths and closed files avoid relying on that detection for old artifacts.

Finite jobs MUST report truthful progress by default; intrinsically indeterminate work MUST use stage descriptions without a fabricated percentage. Both structured and parsed progress require an explicitly enabled compatible library; follow the application's backup/restore and older-writer compatibility procedure before enabling it. Use the structured `run.progress(current=..., total=..., stage=...)` API with the SimShelf package installed in the selected interpreter, OR print a whole-line supported form such as `Step 1000 of 50000` with flushing and explicitly select the **Step counts** parser. Neither adapter is universal automatic inference. SHOULD rate-limit reports and measure instrumentation overhead. Do not conflate step counts with scientific time or consider 100% proof of successful computation. Completed-run display values can be synthesized from process completion; the stored last report is separate, and progress is not a scientific time series.

Where scientifically meaningful, SHOULD call run.metric(name, value, step=..., sim_time=...) from a joined run context, using finite, correctly defined quantities that satisfy Core diagnostic requirements. Invalid/nonfinite measurements can raise in the caller; record and handle such outcomes explicitly. SHOULD also save independent measurements.csv and summary.json. SimShelf does not infer arbitrary log numbers as stored scientific metrics.

Small text JSON/CSV/logs and useful preview images SHOULD usually be copied according to configured limits; large binary captures/checkpoints SHOULD usually be referenced with independently verified backups. File capture rules are prospective, first-match-wins; a source-local .log outside the watched folder is not included merely because it exists.

## 4. Optional Wavez profile

Use the currently supported WVZ1 .wvz format via wavez_export.SceneCapture and its documented reader. Do NOT create obsolete SSC/SIMSCP4 outputs or mislabel a custom file. Preserve actual solver timestamps, scientific units and coordinate meanings; use supported particle/mesh ID semantics and valid volume shape (nz,ny,nx) with xyz origin/spacing. Channel names must reflect actual solver quantities. Declare coordinate transformations, centering and channel meaning explicitly; unknown units remain unknown. Do not invent persistent IDs from row order or silently normalize/narrow scientific values for display. Represent complex fields through documented real components and retain full restart/scientific state separately when needed. The integration guide supplies application-specific geometry and identity API details supporting these SWSS requirements.

### Capture names and run identity

Following [Core's unique-output requirement](#2-core-profile-scientific-integrity), each WVZ1 capture MUST use a new, unused full path. Default filenames SHOULD combine a stable simulation identifier, experiment/case label, UTC timestamp (`YYYYMMDDTHHMMSSZ`) and collision-resistant run ID: `<simulation>_<case>_<UTC timestamp>_<run ID>.wvz`. For example, `vacuum_collapse_D_20261018T164500Z_RUNID.wvz` uses `RUNID` as a placeholder for a full collision-resistant identifier, not a literal suffix. A timestamp alone is insufficient for runs started within the same second. Generate identity independently of the scientific RNG stream.

The same run identifier MUST correlate the capture, log and associated metadata/diagnostic manifests. Record the run ID and resolved capture path in run provenance; multiple captures within one run MUST have distinct artifact labels or sequence suffixes while retaining that run ID. Unique per-run directories can establish full-path uniqueness even when basenames repeat; in that case, document the directory-to-run mapping and still SHOULD use descriptive filenames.

Naming is a simulation-side SWSS convention, not automatic naming by Wavez. Preserve the [Wavez API's exclusive creation](https://github.com/mongstad/Wavez/blob/main/WAVEZ_API.md): captures MUST NOT automatically replace existing files. Collision-resistant names reduce accidental collisions; exclusive creation is the final protection, including concurrent creation races. An explicitly supplied `--wavez-file` (if the simulation offers it) MUST designate a new unused path or fail clearly. It MUST NOT be silently renamed; any alternative-path behavior requires documented, explicit opt-in and recording of the actual path. An existence check alone MUST NOT replace exclusive creation.

An existing destination is a naming collision, distinct from permission denial, invalid/missing parent paths or insufficient disk space. Report the actual failure and destination; unique names do not prevent all filesystem errors. Follow the failure and partial-evidence requirements below.

### Recording and validation

Recording cadence MUST be configurable independently of integration timestep, and recording MUST NOT change scientific RNG calls or solver state. Do not silently overwrite captures. Finalize the writer correctly; partial captures must not be declared verified complete. Each requested `.wvz` artifact MUST undergo matching `SceneReader` validation before being described as verified, with actual payload readback and documented coverage. Acceptance MUST include numerical comparisons against source samples (values/dtypes, geometry, timestamps, units and channels), identity-history checks where applicable, and a viewer inspection on a representative short file. Viewer playback alone does not recompute payload SHA and is not an integrity test. An incomplete trailing record may be inspected with `strict=False`, but that does not accept corruption or establish a complete run. Export failures MUST be reported truthfully; document whether the solver stops or continues and how independent scientific archives are preserved. After an I/O failure the writer is unusable: retain the committed prefix and use a new destination, not writer resume. WVZ1 is visualization data, not a universal restart state. A capture toggle MAY reduce cost, but a Wavez profile claim requires a supplied and tested export path.

## 5. Acceptance and adoption

For **Core**, verify unique paths, version/provenance, truthful success/failure, log and numeric baseline before/after integration. For **SimShelf**, verify discovered settings, correct effective output folder, live progress using a supported selected adapter, metrics if meaningful, native process Logs, and an automatically captured timestamped .log under Files with **no manual upload**. For **Wavez**, verify the real WVZ1 output with both SceneReader numerical comparisons and a Wavez viewer inspection. Run a successful short job, an intentional failure and a handled cancellation where safe; record untested paths. SimShelf acceptance also MUST exercise two simultaneous runs with distinct capture targets, inspect copy/reference budgets and independently compare recorded metrics with solver diagnostics. Wavez acceptance MUST compare export enabled/disabled numerical state and RNG behavior. It MUST also run two consecutive captures with identical scientific parameters using default destination selection, verify distinct paths and separately readable WVZ1 payloads, confirm the first artifact remains unchanged, and check run-ID correlation with logs/metadata. Test an explicit-path collision: it must fail clearly without replacing the existing capture or silently writing to an alternative path when no opt-in is enabled. Verify independent backups for source and referenced artifacts. See the [review gates](../../docs/REVIEW.md).

The first SWSS reference implementation and automated version consistency checks are **future work**, not current certification. Validate one small synthetic simulation before adopting any legacy simulation. No mass migration or historical-data rewrite is required. A reusable starter/helper is future work subject to separate owner approval. Automatic external-log ingestion, automatic source-version bumps, embedding WVZ1 in the SimShelf database, cloud upload, video-derived scientific ground truth and restart from WVZ1 are outside v1.0 requirements.
